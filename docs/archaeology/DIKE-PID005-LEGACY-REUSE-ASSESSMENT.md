## Detailed findings

### 1. Genuine multi-implementation architecture, not accidental duplication

`ls -la /srv-dev/tradingProteus/dike/` → `config.py`, `evaluator.py`, `ledger.py`, `publisher.py`, `auto_publish.py`, `ios_publisher.py`, `strategy_params.py`, `dike_build_run.md`. Five more independent implementations exist elsewhere in the tree: `apollov4/dike_config_processor.py`, `tyche/dike_config_processor.py` + `tyche_dike_processor.py`, `morpheus/execution/dike_gate.py`, `neo/neo_desk/capture/dike.py`, `proteus/dike/processor.py`. This is deliberate: `EPIC-DIKE-002.md` names an explicit `forbidden_services` isolation list, and `WO-0246-DIKE-PROCESSOR-RECREATE.md` explicitly forbids modifying `tradingProteus/dike/*`, marking it "reference only." Any DARWIN `DIKEPolicyVersion` design must decide deliberately whether to unify or preserve this isolation — the legacy answer was preserve, and (see item 8) at least one attempt to unify (`proteus/dike/processor.py`) already violated the isolation doctrine and drifted stale as a result.

### 2–3. Gating logic is the reusable core across all live implementations

`apollov4/dike_config_processor.py::check_gate()` (lines 355-464) implements, in order: (1) regime-aware `effective_max_positions = min(max_open_positions, non_trend_max_positions)` unless `dike_trend_safe=True` (lines 390-406); (2) `MAX_TRADES_TODAY` (409-410); (3) `LOSS_STREAK_LIMIT` (412-414); (4) per-session (`ASIA`/`LONDON`/`NY`) `SESSION_LOSS_LIMIT` (416-424) with a WO-0259 NY-recovery-window conditional override (day-floor hard stop, max NY-recovery losses, macro-strength/chop-score thresholds, lines 466-503); (5) `BURST_LIMIT` — entries in a trailing 30-minute window (451-454); (6) `PROFIT_LOCK` — giveback-from-peak-R (456-461). All tunables load from a `dike_templates` DB table, fail-loud if a required field is missing (lines 258-290). No code path mutates `DikeConfig` from observed outcomes — `record_trade_outcome()` only records; `DikeState` resets daily. `WO-DIKE-STACK-001.md`'s own "Key Design Decisions" explicitly forbid raw `market_state` use inside gate logic (only the precomputed `dike_trend_safe` boolean is permitted), enforced by a contract test (`test_contract_no_market_state_stacking.py`) — a genuine, already-existing architectural safeguard against exactly the kind of hidden self-adaptation WO §13 warns about.

`tyche/dike_config_processor.py` (492 lines) mirrors this logic closely (same 8-step `check_gate`, minus the NY-recovery override, plus WO-0253's stricter fail-loud fields with no defaults). `tyche_dike_processor.py::TycheDikeProcessor` (WO-TYCHE-007, "unified engine — ONE DIKE processor `DIKE_NORMAL`") adds an explicit hard-lock at template-load time:
```python
if lot_multiplier != 1.0:
    raise TycheConfigError(
        "DIKE_NEUTRAL_VIOLATION: ... DIKE gates, it does NOT size. "
        "Someone modified DIKE_NORMAL — this is a sizing drift."
    )
```
This shows the legacy codebase **already self-corrected toward current DARWIN's "DIKE ≠ sizing" doctrine**, via a work order, ahead of any DARWIN ruling — direct evidence the doctrine is not an arbitrary new constraint but one the legacy engineering org converged on independently after experience.

### 4–7, 9. Sizing-in-gating contamination — confirmed, bounded, and correctly classifiable

Sizing logic was found embedded directly inside gating classes in four places: `apollov4/dike_config_processor.py::get_lot_size()` (lines 615-627, `lot = base_lot * lot_multiplier`, clamped to `min_lot_size`/`max_lot_size`), the same pattern in `tyche/dike_config_processor.py` (454-466) and `proteus/dike/processor.py` (574-587), and `dike/strategy_params.py::adjust_position_size()` (91-101, `proposed_size * self.position_size_mult`) — the last one directly contradicting its own module's docstring ("guardrails that validate Zeus template outputs, NOT modifiers that change SL/TP... Templates own SL/TP," lines 33-35, which never disclaims sizing specifically, but the method's presence still conflates a validation module with a sizing-mutation method). `dike/config.py::StreakRules.loss_streak_action` (line 45) compounds this at the schema level — a single field whose value (`"REDUCE_SIZE"` or `"REJECT"`) names a sizing action from inside what is otherwise a gating config object.

Critically, this archaeology **corrects the brief's own background assumption**: the confidence/loss-streak/recovery multiplicative sizing formula described in `EPIC-DIKE-001.md` (`effective_risk = base_risk × lot_multiplier × confidence_factor × streak_factor × recovery_factor`, GOV-SIZING-002, authored 2026-02-02) was never implemented — a repo-wide grep for `confidence_factor` returns zero hits in any of `apollov4/`, `tyche/`, `proteus/dike/`. The epic's own implementation-status table already marked this formula "✗ NOT USED" at authoring time. What survives from that proposal is only dormant, unconsumed DB columns (`loss_streak_multiplier=0.50`, `recovery_size_multiplier=0.50`, `recovery_exit_after_wins=2` on the live `dike_templates.DIKE_NORMAL` row, per `ops/evidence/WO-DIKE-MATURE-0001/profile.txt` and `WO-DIKE-DISCOVERY-MODE-0001/dike_changes.txt`) — vestigial config-schema sizing surface, not executing code. The one place real live sizing math actually lives is `shared/lot_sizing.py::calculate_lot_size()` (ADR-0026/WO-0139), a deliberately cross-service-shared module ("eliminates config drift between Apollo, Tyche, Plutus, Morpheus, Prometheus") — the polar opposite of DIKE's per-service isolation doctrine, and `tyche/trading_engine.py:1225-1230` calls this shared function directly, never `TycheDikeProcessor.get_lot_size()` (confirmed dead in the live call path). **Recommendation for PID-005: DARWIN's future `SizingPolicyVersion` should look to `shared/lot_sizing.py` as its closest legacy analogue, not to any of the sizing methods embedded inside DIKE gating classes.**

### 8. `proteus/dike/processor.py` — a documented isolation-doctrine violation

612 lines, full-read. Its own docstring states: "Canonical DIKE Guardrails Processor. Extracted from `apollov4/dike_config_processor.py`... Shared by: ApolloV4, Tyche, MorpheusV4." This directly contradicts `EPIC-DIKE-002.md`'s `forbidden_services: [zeusv3, apollo, zeus, tyche]` and `WO-0246-DIKE-PROCESSOR-RECREATE.md`'s explicit forbidden-directories list naming `tradingProteus/dike/*` "reference only, DO NOT MODIFY." Content is near-identical to `apollov4/dike_config_processor.py` but is a **stale snapshot** — it lacks the `non_trend_max_positions` regime-aware cap and `dike_trend_safe`/`market_state_for_audit` parameters that `WO-DIKE-STACK-001` (2026-02-12) added to both of its claimed source implementations, meaning this "canonical shared" extraction was never kept in sync with either divergent original it claims to unify. It additionally contains its own `get_lot_size()` sizing method (item 4) and a 2-value `DikeAction(ALLOW, REJECT)` enum, distinct from `dike/evaluator.py`'s 4-value `ALLOW/REDUCE_SIZE/REJECT/CLOSE_ONLY`. **Do not treat this file as architecturally authoritative for any DARWIN migration** — it is evidence of a governance breach and a drift artifact, not a clean shared abstraction.

### 10–12. Clean, reusable components

`dike/ledger.py` (96 lines, full file) is a pure abstract data contract (`LedgerState` dataclass + `LedgerProvider(ABC)`) with no logic and therefore no doctrine violations to inherit — directly reusable as an interface pattern. `dike/strategy_params.py`'s `validate_sl_distance()`/`validate_rr_ratio()` (lines 48-89) are sound pure-validation methods returning `(bool, reason)`, adaptable once split from `adjust_position_size()`. `neo/neo_desk/capture/dike.py` (60 lines, full file, actual path under `/srv-dev/tradingProteus/neo/neo_desk/capture/`, not the top-level path the brief initially assumed) is confirmed genuinely passive: `capture_dike_snapshot()` builds a payload hash and does `INSERT IGNORE INTO neo_desk_dike_snapshots` with an `ON dedup(instrument, snapshot_ts)` uniqueness guard, returning `snapshot_id` or `0` on duplicate — no decision, gate, or sizing logic anywhere in the file. This is a clean, doctrine-compliant "observe only" pattern (WO §12's NEO-may-observe-and-hypothesise boundary).

### 13–14. Human-gated, evidence-based parameter change is the correct legacy pattern to reuse

`WO-DIKE-DISCOVERY-MODE-0001.md` (2026-03-22, COMPLETE) explicitly labels itself "Paper Observation Posture" and neutralises nearly all DIKE throttles (max positions 4→20, trades/day 15→100, daily-loss-cap 3%→50%, drawdown-cap 5%→50%, loss-streak-threshold 3→100, streak/recovery multipliers →1.0), scoped explicitly to paper/discovery trading only, with documented rollback SQL. `WO-DIKE-MATURE-0001.md` (same day, COMPLETE) then restores real guardrails (4 positions/instrument, 20 trades/day, 10% daily-loss, 15% drawdown) while *deliberately* leaving cooldowns/loss-streak-reduction/recovery-mode disabled, citing "no evidence they help" from the discovery-mode replay. This is precisely WO §13's canonical model in miniature — `observation → hypothesis → evidence → explicit versioned change → approval` — executed by a human-approved Work Order, never runtime self-mutation. This pairing is a strong process pattern to carry into PID-005/006's own DIKE-research workflow, independent of any specific parameter values it used.

### 15. iOS CDN sizing payload — a genuine open gap

`dike/ios_publisher.py` (339 lines, full file) builds an `IOSRiskProfile` payload per LOW/MEDIUM/HIGH risk tier containing `lot_multiplier`, `loss_streak_multiplier`, `recovery_size_multiplier` (lines 54-64), published via SFTP/CDN to `https://mt.noust.ai/decisions/settings/settings.json` for iOS Morpheus consumption. The payload shape is unambiguously sizing-shaped on the backend side. Whether the Swift-side consumer applies these values as position-sizing multipliers or as some gating-adjacent behaviour was **not verified** — the Swift code lives outside the `tradingProteus` Python tree and was out of scope for this pass. This is flagged as an explicit open question (see the boundary/recommendations document) rather than assumed either way.

### 16. No learned/self-adaptation found anywhere

Across all six implementations, `DikeState`/config objects are populated exclusively from DB-declared templates (fail-loud on missing fields) and updated only via `record_trade_outcome()`-style outcome recording, which never feeds back into the config/thresholds themselves at runtime. The only parameter changes found anywhere in the legacy history were human-authored Work Orders (item 13-14). No code path anywhere constitutes the WO §13-forbidden pattern of "live observation → model changes DIKE directly."
