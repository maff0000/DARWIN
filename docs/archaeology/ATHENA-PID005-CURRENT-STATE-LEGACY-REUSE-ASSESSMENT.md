### 5–8. Legacy ATHENA is two coexisting search systems, not one

`/srv-dev/tradingProteus/athena/` contains two independently-built optimisation harnesses that were never unified:

**A) `optimizer.py::AthenaOptimizer`** ("ML-Driven Parameter Search", its own docstring) — the older lineage:
- `generate_configs_grid()` (lines 123-149): full-factorial `itertools.product` grid, deterministic, combinatorial-explosion risk with parameter count.
- `generate_configs_random()` (lines 151-177): `random.uniform`/`random.choice`, default `n=100` (config.py:261). **No `random.seed()` call exists anywhere in the file** (confirmed by grep across all `athena/*.py`) — two identical invocations sample different candidates. Not reproducible.
- `generate_configs_around_best()` (lines 179-219): despite being marketed as "refinement (Bayesian)" in the module docstring and CLI framing, this is uniform-random perturbation around a single incumbent — no surrogate model, no acquisition function. The "Bayesian" label must not be copied into any DARWIN documentation; the mechanism itself (local random perturbation around an incumbent) is adaptable as a plain "local random refinement" stage if DARWIN wants it, clearly labelled as such.
- Sampled/declared parameter values are drawn strictly within `ParameterRange.min_val/max_val` (config.py:191-197) for the parameters actually reaching the sampler — but see the more serious Finding below.

**B) `run_nowic_sweep.py` + `sweep_core.py` + `hash_pipeline.py`** ("WO-ATHENA-NOWIC-SWEEP-0003") — a later, materially stricter successor:
- `build_combo_grid()` (sweep_core.py:15-48): full-factorial grid, canonically sorted via `make_combo_id()`, zero randomness anywhere in the module (confirmed by grep — no `random`/`seed` import at all).
- Explicitly engineered to *prove* serial/parallel result parity via a 3-layer hash pipeline (decision-level, trade-level, economic-level hashes; `hash_pipeline.py`) comparing a `workers=1` "golden reference" run against a parallel run.
- No pruning, successive-halving, genetic/evolutionary, or true Bayesian technique found in either lineage — only full grid and (in `optimizer.py` only) unseeded random/local-perturbation search.

**Finding — silent parameter drop (new, not previously surfaced by CD-0):** `ConfigCandidate` (`config.py:340-374`) declares 8 tunable fields, but `ConfigCandidate.build_zeusv3_overrides()` (`config.py:393-436`) — the *only* function that builds what actually reaches the backtest engine (`runner.py:116`) — hardcodes a 4-key dict:
```python
param_values = {
    'sl_atr_multiple': self.sl_atr_multiple,
    'tp_atr_multiple': self.tp_atr_multiple,
    'base_confidence': self.base_confidence,
    'min_confidence': self.min_confidence,
}
```
If the DB (`athena_param_ranges`) declares search ranges for `rsi_floor`, `rsi_ceiling`, `ema50_200_diverging_bonus`, or `risk_per_trade`, the optimiser samples and persists candidate values for them (`optimizer.py:393-408` writes `rsi_floor`/`rsi_ceiling` to `athena_results`), but those values are **never transmitted to Apollo/ZeusV3** — every candidate is backtested at whatever fixed/base value those 4 parameters hold, regardless of what the results table claims was searched. No warning or assertion surfaces this gap anywhere in the code. **This must not be carried into DARWIN**: any override-builder in a DARWIN ATHENA must derive its transmitted-parameter allowlist mechanically from the authorised search envelope (`PolicySearchAuthority`/tunable-parameter declarations), never from a hand-maintained fixed dict that can silently drift out of sync with what the specification actually authorises.

### 9–11. Objective/ranking safety — a systemic gap, confirmed across all four independent implementations

Four separate, non-unified scoring/ranking formulas exist in legacy ATHENA, and **none of them carries a minimum-trade-count guard**:

1. `runner.py::AthenaRunner._build_result` (lines 178-198): `profit_factor = gross_profit/gross_loss if gross_loss>0 else 99.0`; `score = (net_pnl/max_drawdown_pct)*(win_rate/100) if win_rate>0 else risk_adjusted`.
2. `optimizer.py::AthenaOptimizer.run` (line 285): sorts purely on formula (1)'s score, no trade-count filter anywhere in the file.
3. `athena_tcs2_wrapper.py::_convert_results` (lines 148-152): `score = total_pnl / max(max_drawdown_pct, 0.1)` — a third, simpler formula, no win-rate term, no profit-factor term, sorted directly (line 200).
4. `sweep_core.py::rank_combos` (lines 308-332): `sort_key = (-expectancy, -profit_factor, max_drawdown_r, -total_trades, combo_id)` — the only formula with any trade-count awareness at all, and even there `total_trades` is tiebreak #4, not a filter; `profit_factor` in this module (lines 165-170, 266-270) evaluates to `999.99` for any all-win sample, which combined with rank-key position #2 gives near-guaranteed top rank to tiny-sample all-win combinations unless expectancy differs.

This confirms WO §17's danger class ("tiny-trade-count winners") is real and systemic across the legacy codebase, not a single-function oversight — **any DARWIN ATHENA scoring/ranking function must carry an explicit, non-optional minimum-sample-size gate**, and ideally reject rather than merely down-rank statistically insufficient candidates.

**Compounding drawdown-blindness finding:** `main.py:83` defaults `dike_enabled=False` for the wide search, and when disabled, `runner.py:140-149` sets `drawdown_trigger_pct=99.0`, `max_daily_loss_pct=99.0`, `max_single_position_pct=99.0`, `loss_streak_threshold=999`, `loss_streak_action='CONTINUE'` — i.e. the drawdown term inside every one of the above scoring formulas is computed from a backtest run under an artificially unconstrained risk regime that live/guarded trading would never permit. A config can win legacy ATHENA's search specifically *because* DIKE was neutered, and that dependency is invisible in the score. This is a distinct risk from "DIKE_DISABLED is a legitimate research baseline" (WO §11, which remains true) — the finding is that the *scoring function itself* does not account for which regime produced the drawdown number it is rewarding.

**Other config-wiring defects found, unrelated to the danger-class checklist but worth recording as legacy code-quality evidence:** `runner.py:128` — `risk_profile='HIGH' if not self.dike_enabled else 'HIGH'` is dead code (both branches identical); `optimizer.py:254-255` sources `starting_balance` from `load_apollo_config_from_db('LOW')` while the actual `ApolloConfig` risk_profile is hardcoded `'HIGH'` — a genuine mismatched-config bug independent of any DARWIN doctrine question.

No mitigation was found anywhere in legacy ATHENA for parameter cliffs, regime dependence, multiple-testing correction, or lookahead — these remain open design questions for PID-005, not solved problems to inherit.

### 12–13. Temporal correctness and intrabar semantics are entirely Apollo's concern, not ATHENA's

`runner.py:125-138` shows ATHENA bounding every replay call with explicit `start_date`/`end_date` and `dry_run=True` before invoking `ApolloEngine.run()`; `run_nowic_sweep.py` does the equivalent via `--start`/`--end` CLI args to a subprocess invocation of `apollov4.run`. This confirms ATHENA does not hand Apollo the full indiscriminate dataset — but whether the replay itself is bar-by-bar lookahead-safe, and what SL/TP same-candle resolution order it assumes, is **entirely inside `apollo/replay_engine.py` and `apollov4/engine.py`**, both explicitly out of the `athena/`-scoped read performed here. Grep across all of `athena/*.py` for sl/tp/intrabar/wick ordering logic found none — ATHENA genuinely has no opinion on wick/intrabar semantics; it is a pure config-search/scoring harness around whatever Apollo decides. **This is a hard scope boundary, not a gap in this archaeology**: a dedicated Apollo-focused archaeology pass (feeding PID-006) is the correct place to answer WO §18/§19 definitively; this document can only confirm ATHENA's own code carries no conflicting assumption.

### 14–15. Execution blindness and instrument genericity — legacy ATHENA is already clean here

Grep across all `athena/*.py` for `broker|account_id|oanda|ibkr|mt5|host=|hostname` found exactly one hit — `athena_tcs2_wrapper.py:92`, a debug-only Redis host env-var default (`os.environ.get('REDIS_HOST', '127.0.0.1')`, gated behind `debug=True`, off by default) — not a broker/account/venue binding. No hardcoded broker, account ID, or live-execution venue reference exists anywhere in the directory; ATHENA only ever talks to Apollo in `dry_run=True` and to research/backtest DB schemas (`tradingProteus`/`tradingSignals`/`tradingRisk`), never broker/account tables.

Grep for `XAU|gold|pip|lot_size|decimal_place|GBP|EUR_USD` found `instrument='XAU_USD'` used only as an overridable default parameter value in five places (`config.py:253`, `main.py:92-93`, `optimizer.py:452,498`, `runner.py:65`) — never inside a conditional branch. The newer `run_nowic_sweep.py` improves on this further: `--instrument` is `required=True` with no default at all ("GOV-CFG-001"), and its own CLI documentation/examples use `EUR_USD`. Both execution-blindness and instrument-genericity are therefore REUSE-clean properties of the legacy ATHENA code as written — a genuinely positive finding, not something DARWIN needs to rebuild.

### 16–17. Parallelism — two different models, one materially more mature

`optimizer.py::AthenaOptimizer` uses stdlib `multiprocessing.Pool`, auto-sized to `cpu_count()-1` workers (line 107); each worker constructs its own `AthenaRunner`/`ApolloEngine`/`DataLoader` per call (confirmed: dataset reloaded per-process-per-call, never shared or memory-mapped); dispatch is ordered `pool.map` (line 280), so result-to-config mapping is deterministic *given identical inputs*, but config generation itself is unseeded (see above), so no run-to-run reproducibility exists end-to-end. **Zero checkpointing**: `_record_results()` (persisting to DB) runs only once, after the *entire* `pool.map` call returns — a single killed worker process loses the whole batch's unwritten results. In-worker exceptions are caught and scored `-999999.0` rather than propagating (lines 51-84), so an exception (as opposed to a killed process) does not lose the batch.

`run_nowic_sweep.py::_run_combos_parallel` is materially more careful: a `Pool` initializer plus `Manager().Queue()` hands each worker a distinct, pre-created DB `plan_id` so workers never share mutable DB override state; each combo additionally runs as its own OS subprocess (`subprocess.run([..., '-m', 'apollov4.run', '--dry-run', ...])`) — double-isolated, heavier (dataset reloaded per combo, not just per worker) but maximally safe against state bleed. Dispatch uses `imap_unordered` (results stream back in completion order) followed by an explicit `results.sort(key=lambda r: r['combo_id'])` to restore determinism — a correct, deliberate fix for the nondeterminism `imap_unordered` would otherwise introduce. Still **zero checkpointing at the sweep level** (bulk-persist to `athena_nowic_sweep_results` happens once, after all combos return), though each combo's own CSV export and hash sidecar survive on disk in `tmp_dir` and could theoretically be manually recovered — a materially better crash-recovery posture than `optimizer.py`, though not true checkpointing. A worker-cleanup gap was also found: the `finally` block that deactivates `plan_id` rows on completion does not run if the whole process is SIGKILLed, leaving orphaned `is_active` rows in `apollov4_backtest_plans` — a known, non-fatal DARWIN-relevant cleanup pattern to avoid repeating.

Both lineages use pure OS-process parallelism (no threading, no asyncio, no GPU/vectorised batch execution) — appropriate for CPU/IO-bound backtest-replay workloads and consistent with WO §22's "single-host first, no premature microservices" guidance.

## PID-005 consequences (summary)

- The current DARWIN scaffolding (lifecycle enum, evidence-level enum, immutable MarketDataset, policy search-envelope model, ResearchRun/EvidenceRecord persistence shape) is **already correctly designed** for ATHENA to be built against — no rework of Foundation is implied by this archaeology.
